# スタンプ作成フローのアーキテクチャ

## 1. 概要

このドキュメントは、「AI LINE Sticker Generator」アプリケーションにおけるスタンプ作成機能のアーキテクチャとデータフローを詳細に解説します。この機能は、ユーザーが選択または生成したキャラクターデザインを基に、AIを活用して複数のLINEスタンプを効率的に作成することを目的としています。

全体のフローは以下の主要なステップで構成されます：
1.  **キャラクター選択**: ユーザーはスタンプの元となるキャラクターを選択します。
2.  **生成設定**: スタンプの個数やテキストのスタイルなどを設定します。
3.  **テキスト生成**: AIがキャラクター設定に基づいて、スタンプ用のセリフを複数提案します。
4.  **画像生成**: AIがキャラクターとセリフを組み合わせて、スタンプ画像を生成します。
5.  **修正と編集**: ユーザーはAIが生成したテキストや画像をさらに微調整できます。
6.  **ダウンロード**: 完成したスタンプを個別または一括でダウンロードします。

## 2. 主要コンポーネントと役割

スタンプ作成機能は、責務が明確に分離された複数のコンポーネントとサービスによって実現されています。

- **`components/StickerCreationTab.tsx`**:
  - スタンプ作成タブ全体のUIと状態管理を担当するメインコンポーネント。
  - キャラクターの選択、生成設定、API呼び出しのトリガー、生成されたスタンプの一覧表示など、すべてのユーザーインタラクションを処理します。

- **`components/StickerCard.tsx`**:
  - 個々のスタンプを表示・編集するためのカード型コンポーネント。
  - スタンプの現在の状態（生成中、完了、エラーなど）を視覚的に表示し、テキストの編集や修正モーダルの起動、個別ダウンロードの機能を提供します。

- **`components/RevisionModal.tsx`**:
  - 既存のスタンプ画像をAIで対話的に修正するためのモーダルウィンドウ。
  - ユーザーからの修正指示を受け取り、リアルタイムでプレビューを更新し、変更を適用する機能を提供します。

- **`services/geminiService.ts`**:
  - Gemini APIとの通信を担当するサービス。
  - `generateStickerTexts`, `generateStickerImage`, `reviseStickerImage` といった関数を通じて、テキスト生成、画像生成、画像修正の具体的なAPIリクエストを抽象化します。

- **`services/aiConfigService.ts`**:
  - AIに送信するすべてのプロンプトテンプレートを管理するサービス。
  - `AITask.STICKER_TEXT` や `AITask.STICKER_IMAGE` など、タスクごとにプロンプトが定義されており、一元管理とユーザーによるカスタマイズを可能にしています。

## 3. データフローとユーザーストーリー

ユーザーがスタンプを作成する際の具体的なフローを順を追って説明します。

### 3.1. キャラクターの選択

スタンプ作成は、まず元となるキャラクターを決定することから始まります。ユーザーには3つの選択肢があります。

1.  **3面図作成タブからの遷移**: `CharacterDesignTab` でキャラクターを生成後、「この画像でスタンプを作成する」ボタンを押すと、そのキャラクター(`CharacterDesign`オブジェクト)が`StickerCreationTab`に`initialDesign`として渡されます。
2.  **履歴からの選択**: サイドバーやタブ内の履歴リストから、過去に生成したキャラクターを選択できます。
3.  **カスタム画像のアップロード**: ユーザーはPCから任意のキャラクター画像をアップロードして、それをベースにスタンプを作成することも可能です。

### 3.2. 生成設定

キャラクターが選択されると、ユーザーは生成パネルで以下の項目を設定します。

- **スタンプ個数**: 8個、16個、24個から選択。
- **口調・雰囲気**: 「丁寧語」「タメ口」など、テキスト生成時のトーンを定義。
- **文字の装飾**: 「ポップ」「手書き風」など、画像生成時のテキストスタイルを指示。

### 3.3. テキストの一括生成

1.  ユーザーが「文字のデザインを生成」ボタンをクリックします。
2.  `StickerCreationTab`の`handleGenerateTexts`関数が実行されます。
3.  `geminiService.generateStickerTexts`が呼び出されます。この際、キャラクター設定、スタンプ個数、口調、装飾が引数として渡されます。
4.  サービスは`aiConfigService`から`AITask.STICKER_TEXT`のプロンプトを取得し、引数でテンプレートを埋めます。
5.  Gemini API (`gemini-2.5-flash`) にJSON形式のレスポンスを要求するリクエストが送信されます。
6.  APIから返されたテキストリストが`stickers`状態にセットされ、各`StickerCard`のテキストエリアに表示されます。この間、カードのステータスは`generating_text`となり、UIが更新されます。

### 3.4. 画像の一括生成

1.  ユーザーが「スタンプ画像を生成」ボタンをクリックします。
2.  `handleGenerateImages`関数が実行されます。ここには**バッチ処理**という重要な最適化が実装されています。
3.  全スタンプを一度に処理するのではなく、`BATCH_SIZE`（現在は4）で定義された数ずつのグループに分割します。
4.  Promise.allを使用して、バッチ内のスタンプ画像を並列で生成します。これにより、APIへの過剰なリクエストを防ぎ、ブラウザのパフォーマンスを安定させます。
5.  各スタンプに対して`geminiService.generateStickerImage`が呼び出されます。引数として、ベースとなるキャラクター画像、スタンプテキスト、キャラクター設定が渡されます。
6.  サービスは`AITask.STICKER_IMAGE`のプロンプトを使用し、`gemini-2.5-flash-image-preview`モデルに画像生成を依頼します。
7.  生成された画像データ(Base64)とファイル名が返され、対応するスタンプの`image`と`fileName`プロパティが更新されます。ステータスは`generating_image`から`done`または`error`に変わります。
8.  一つのバッチが完了すると、次のバッチの処理が開始されます。

### 3.5. 個別の修正と編集

- **テキスト編集**: ユーザーは各`StickerCard`のテキストエリアで、AIが生成したテキストをいつでも手動で編集できます。
- **AIによる画像修正**:
  1.  ユーザーが「AIで修正」ボタンをクリックすると、対象の`Sticker`オブジェクトと共に`RevisionModal`が開きます。
  2.  ユーザーはモーダル内で「もっと楽しそうな表情にして」といった自然言語で修正指示を入力します。
  3.  「依頼」ボタンを押すと`reviseStickerImage`サービスが呼び出され、`AITask.REVISE_STICKER`プロンプトを基に画像が再生成されます。
  4.  モーダル内のプレビューが新しい画像に更新されます。ユーザーはこのプロセスを何度でも繰り返すことができます。
  5.  満足のいく結果が得られたら、「このデザインを適用」ボタンを押し、`StickerCreationTab`の`stickers`状態に変更が反映されます。

### 3.6. ダウンロード

- **個別ダウンロード**: 各カードのダウンロードアイコンから、そのスタンプ画像（例: `stamp_01_thankyou.png`）を直接ダウンロードできます。
- **一括ダウンロード**: 「一括ダウンロード」ボタンを押すと、`JSZip`ライブラリを使用して、ステータスが`done`のすべてのスタンプ画像を一つのZIPファイル（例: `キャラクター名_stickers.zip`）にまとめてダウンロードします。

## 4. 技術的な特徴とこだわり

この機能の実装には、優れたユーザー体験とパフォーマンスを実現するためのいくつかの工夫が凝らされています。

- **非同期バッチ処理**: 画像生成は時間のかかる処理であり、多数のスタンプを同時にリクエストするとAPI制限やブラウザのフリーズを引き起こす可能性があります。これを避けるため、リクエストを小さなバッチに分割して順次処理する仕組みは、アプリケーションの安定性を大幅に向上させています。
- **詳細な状態管理**: 各スタンプが個別の状態（`StickerStatus`）を持つことで、UIは生成プロセスの進捗をきめ細かくユーザーにフィードバックできます。カードの枠線の色やオーバーレイ表示により、どのスタンプが処理中、完了、またはエラーになったかが一目でわかります。
- **プロンプトの抽象化**: すべてのプロンプトを`aiConfigService`で一元管理することで、コードの可読性が向上し、将来的なプロンプトの変更や追加が容易になっています。また、設定画面を通じてユーザー自身がプロンプトをカスタマイズできるため、アプリケーションの柔軟性が高いです。
- **非破壊的な編集フロー**: `RevisionModal`では、修正内容を適用するまで元の画像が変更されない「プレビュー」機能が提供されています。これにより、ユーザーは安心して様々な修正を試すことができます。
